# CTNP v3.1 三角洲实机测试

## 结论

**三角洲大厅中自动下发、两个真实线程匹配和退到桌面恢复均通过。**

已对当前 CTNP 路径及记录到的告警作检查，未确认可归因于 CTNP 的缺陷；因此没有为
“尝试修复”而修改其它调度模块、强开 CTB、绕过内核告警或改动内核指针。
本次不是完整对局／帧率／功耗验收，内核日志也不是零告警。

## 自动下发与匹配

COSA 数据库仅取稳定 DB/WAL 的私有副本并只读查询，三角洲的 `game_config` 是171字节
明文 JSON，其中 `ctn="GameThread RenderThread"`。没有使用 `ctn.conf`、手改数据库、
`game_pid`、`rt_info` 或线程名单。

| 项目 | 实际结果 |
|---|---|
| 自动下发 | 节点为 `GameThread:9830,RenderThread:11148`，与真实COSA配置一致 |
| 第一槽 | PID9830，comm=`GameThread`，Tgid9326 |
| 第二槽 | PID11148，comm=`RenderThread`，Tgid9326 |
| 持续观察 | 约28秒九次采样，两个槽的名字／PID均保持不变，daemon未重启 |
| 游戏中只读Action | 退出0，报告登记名称匹配；未写节点、暂停服务或改动游戏支持状态 |
| HOME退到桌面 | `game_pid=-1`，自动恢复 `UnityMain:-1,UnityGfxDevice:-1` |
| 退出后观察 | 约18秒八次采样均为原名单、enable0、恢复债务 absent |
| 最终状态 | version3.1，服务／daemon仍运行，无`.service.stop`、`exercise.state`或`restore.state`残留 |

生产日志及内核独立记录：

```text
[11-15 09:11:21] ctnd: critical_task_name applied [GameThread RenderThread]
[11-15 09:23:18] ctnd: critical_task_name restored
[33700.456967] ctn_patch: names [GameThread:9830] [RenderThread:11148]
[34417.792626] ctn_patch: names [UnityMain:-1] [UnityGfxDevice:-1]
[34417.793051] ctnd: critical_task_name restored
```

实际线程归属由 `/proc/<tid>/status` 的 Tgid 与游戏 PID交叉确认，不只凭线程名。
同名的其它 `GameThread` 不被冒充为这两个已确认槽的样本。
`ct_enable` 本次保持0；它由系统／HAL管理，CTNP默认 CTB unmanaged，未为测试强行开启。
线程匹配正确不等于已经证明性能收益。

## 告警检查与修复判断

当前下发标记到退出的内核记录保留在相互重叠的快照中；不是全量开机日志，也不凭
时间范围承诺没有任何环形日志丢失。

- 下发标记33700.456967之后发现 **1条内核 WARNING**，时间33715.324970，距标记约14.868秒。
- CPU3、PID12127、comm=`Thread-247`；位置为 `kernel/sched/core.c:3107`，涉及
  `__set_cpus_allowed_ptr_locked`。
- 短调用链经过 `recvfrom → TCP接收/ACK → ip_output → __cgroup_bpf_run_filter_skb →
  migrate_enable → __set_cpus_allowed_ptr_locked`，没有 CTNP函数。
- active-confirmed与lobby-after快照中是同一条WARNING，去重计1，不把重复快照算两次。
- 同轮更早的4条WARNING位于33641.440375–33641.444809，早于当前下发标记约59秒，
  不混算为“CTN下发后”告警；普通面板／DRM的warn文本也不混算成内核断言次数。
- 从已复核大厅快照末尾34296.809324到最终快照34521.063022，没有新增
  BUG／WARNING／Oops／panic／KCFI／KASAN诊断；包含退出恢复的内核日志。

针对已保存的告警与 CTNP模块写入／PID显示路径的只读审查，没有找到直接操纵
runqueue锁、CPU亲和性或balance callback的CTNP路径。**调用栈不含CTNP并不证明间接
关系绝不存在**；也没有做停用CTNP的对照。因此根因未确定、暂无可验证的CTNP修复依据。

本轮没有停用Scene或改其它模块，未关闭告警／SELinux、热卸载KO或追加重启。
若继续定位告警，需要另行确认仅CTNP的启用／停用对照，不能把猜测当补丁依据。

## 证据与范围

原始证据仅留忽略的 `out/v3.1-20261114/delta-real-20261115-01/`：

- `active-confirmed/`：运行身份、游戏包名、线程清单、自检和内核日志。
- `cosa-readonly/`：稳定私有数据库副本及仅三角洲的查询结果，不提交真实库。
- `lobby-thread-ownership.txt`、`lobby-samples/`：准确线程归属和九次连续样本。
- `lobby-readonly-action.txt`：真实退出0、名单及service/daemon未改变。
- `after-home/`：八次原值恢复样本。
- `dmesg-lobby-after.txt`、`final-after-exit/`：最终恢复、运行身份与告警复查窗口。

首次采集因脚本转义和USB断线没有完整状态，不作为成功证据；随后已取得准确的
active-confirmed快照，没有因此改动生产代码。
退到桌面后游戏进程可继续后台驻留，但HAL `game_pid=-1`，`rt_info` 返回“No such process”
与无活跃游戏登记一致，未将它冒称为CTNP恢复失败。

未进入或操控正式对局；未验证帧率、功耗、CTB实际收益、全部游戏阶段或141对应实机。
本轮仅保存测试记录，CTNP版本和生产代码不变，没有提交、推送或替换发行附件。
