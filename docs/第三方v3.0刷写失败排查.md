# 第三方 v3.0 刷写失败排查

## 截图能确认什么

报错发生在 `static installation check (no insmod, no node writes)` 之后，最终提示
`profile/vendor/KO identity check failed; nothing was loaded`。这说明已进入适配检查，
**没有加载 KO，也不是游戏 CTN 下发失败**。

它不同于初始化阶段的 `invalid module identity`。截图没有显示具体拒绝分支、机型、
完整内核版本或厂商文件哈希，不能据此认定根因。`Current boot slot: _b` 只是当前启动槽位，
不是故障依据；安装器显示的 Module size 也不能代替 ZIP SHA256 身份。

## 新版已有的处理

v3.1 保留 BusyBox 裸 `sh` 的初始化修复，并把具体失败原因及处理提示直接输出到
管理器可见的 stdout，不依赖 stderr 是否被第三方管理器展示。安装日志仍由 Root 管理器保存，
模块不另外创建安装日志。

对本次反馈补充了十个隔离失败场景，分别验证普通 sh 和 mksh：

- 未支持的内核、未核验的完整内核版本、CPU 架构不匹配。
- 16K 页、getconf 读取失败。
- profile 清单损坏、manifest 损坏、KO 损坏、daemon 损坏。
- 厂商 game_opt 文件不匹配。

全部场景均在管理器可见输出中给出 `[失败]`、具体原因和 `处理：`，并拒绝安装；
没有 insmod/rmmod、节点写入或额外安装日志。这些回归验证**错误可见性与安全拒绝**，
不是该用户设备已兼容的证明。本轮没有因此修改生产脚本或取消 ABI 校验。

## 需要失败用户补充的材料

先提供：

1. 管理器保存的**完整安装日志**，不是最后几行截图；同时注明管理器名称与版本。
2. 机型、系统／固件完整版本，所刷 ZIP 的文件名和 SHA256。
3. 完整 `uname -r`、`uname -m`。

如果完整日志仍未明确原因，可在该用户自己的设备只读执行：

```sh
uname -r
uname -m
getprop ro.product.model
getprop ro.build.display.id
getconf PAGE_SIZE
getconf PAGESIZE
su -c 'sha256sum /vendor/lib/modules/oplus_bsp_game_opt.ko /vendor_dlkm/lib/modules/oplus_bsp_game_opt.ko'
```

其中命令缺失、路径缺失也保留原始错误，不用假值填补。不要在别人的设备试载本机 KO、
强行覆盖版本字符串或关掉安全校验。如果完整 release 或厂商文件身份尚未核验，需要取得
该设备实际 ABI 基线再决定能否适配。

本次反馈的具体根因仍为**未确认**，不会将“升级3.1后能看见原因”写成“对方已修好”。
